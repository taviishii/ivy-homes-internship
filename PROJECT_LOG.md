# Project Log — Ivy Homes Software Engineering Internship Assignment

A detailed, chronological record of how this assignment was approached and executed, including the reasoning behind every major decision. Written for anyone (including future-me) who wants to understand not just *what* exists in this repo, but *why* it looks the way it does.

An LLM (Claude Code, running Claude Sonnet 5) was used throughout this work, as the assignment explicitly permits and expects. This log itself was produced collaboratively with it, from the actual session transcript.

---

## 1. The assignment, in brief

Ivy Homes runs a property API (`https://solve.ivy.homes`) for a specific Indian city, scoped per candidate by an API key. The documentation (`API_REFERENCE.md`) was deliberately generated by an AI from an old changelog and is explicitly *known to be wrong in places* — some endpoints don't exist, some exist at different paths, some fields are in the wrong units, some parameters are silently ignored. The live API itself is described as honest and healthy; the documentation is what's untrustworthy.

The assignment has three parts:

1. **Build a frontend** — a working property marketplace app with six required capabilities: login, browsable/filterable listings, a listing detail page, saved listings, rentals + projects browsing, and an insights screen.
2. **Answer ten data questions** (Q1–Q10) about the assigned city's dataset — record counts, unique properties, corrupt/fake listing detection, pricing statistics, timestamp-window counts, and so on — all as of a fixed reference moment (`2026-09-10T00:00:00+05:30`).
3. **Document every real discrepancy** between the documentation and the live API as a structured "finding," with evidence, while being graded on precision as much as recall — a padded findings list scores *worse* than a short, accurate one.

The explicit meta-point of the assignment, stated directly in `statement.md`, is that pointing an LLM at the API and asking it to diff the docs against a few sample responses will only get you so far. The real signal is in hypothesis-driven analysis across the *entire* dataset — noticing a pattern, forming a testable theory about *why* the data might be wrong or inconsistent, and proving or disproving it against thousands of records. That framing shaped almost every investigative decision below.

---

## 2. Overall shape of the work

The work was explicitly sequenced into phases, and — critically — the frontend was **not** started until the data investigation and all ten answers were independently validated. Building the UI first, then discovering during that build that half the underlying assumptions about the API were wrong, would have meant redoing everything. The phases:

| Phase | What it covered |
|---|---|
| A | Repository and secrets hygiene before touching the live API |
| B | Controlled API reconnaissance — endpoint-by-endpoint behavior vs. documentation |
| C | Full dataset retrieval (all listings/rentals/projects, paginated to completion) |
| D | Hypothesis-driven analysis to answer Q1–Q10 and find documentation discrepancies |
| E | An adversarial *independent* re-validation pass on the Phase C/D answers |
| F | Final findings audit — reducing everything to only what could be defended |
| G | Frontend implementation, built against the now-verified API behavior |
| — | Git history cleanup (removing tool-attribution trailers per request) |

## 3. Phase A — Repository and security setup

Before any API call was made, the basics were verified rather than assumed:

- Confirmed `.env.local` (holding `IVY_API_KEY` and `IVY_API_BASE_URL`) was present, correctly formatted, and covered by `.gitignore`'s `.env*` pattern.
- Verified the key could be read from the environment in a script *without ever printing it* — every diagnostic script written from this point on redacts secrets before logging.
- Added the demo account password and the assigned locality to `.env.local` as two more environment variables (`IVY_DEMO_PASSWORD`, `IVY_ASSIGNED_LOCALITY`) rather than pasting them into chat, keeping them out of the conversation transcript entirely.
- Added `/analysis/raw/` and `/analysis/log/*.jsonl` to `.gitignore` up front, since the plan was to download and cache large raw API dumps locally for analysis — those should never be committed (large, derived, and potentially containing seller phone numbers at record-level scale).

**One incident, corrected immediately:** an early throwaway test script's log-redaction helper checked for a field literally named `token`, but the real login response uses `access_token`/`refresh_token` — so on one occasion a full token pair printed to the terminal in this session. As soon as this was noticed, the redaction helper was rewritten to catch every secret-shaped field name generically, and the exposed token was invalidated via the logout endpoint as a precaution (see Phase B for why that precaution turned out to be theoretical — logout doesn't actually revoke tokens server-side). The token's own 15-minute lifetime and demo-account-only scope limited the real exposure window regardless. This is called out explicitly here because it's exactly the kind of mistake the assignment's security requirements exist to catch, and hiding it would defeat the point of writing this log.

## 4. Phase B — API reconnaissance

With hygiene confirmed, the documented behavior was tested piece by piece against the live API, starting with the simplest possible check (`GET /health`, unauthenticated) and working up through auth, pagination, and each resource endpoint. Roughly 90 requests were used for this phase — well inside the stated 1200/minute limit.

Key discoveries, each independently reproduced before being written down:

- **Auth key delivery is wrong in the docs.** The documented `?api_key=...` query parameter is rejected outright with a `401` whose own error message says to use an `X-API-Key` header instead. Every request from this point on used the header.
- **Login response shape is wrong.** Docs promise `{token, expires_in: 86400, user: {email, name}}`. The real response is `{access_token, refresh_token, expires_in: 900, refresh_url, user: {email}}` — a completely different field name, a 15-minute token lifetime instead of 24 hours, no `name`, and an undocumented refresh token.
- **A refresh flow exists despite the docs saying "There is no refresh flow."** Discovered because the login response itself contains a `refresh_url` field pointing at `/auth/refresh`. This turned out to be load-bearing for the frontend's "still working 30 minutes after login" requirement, since access tokens really do expire every 15 minutes.
- **Logout doesn't invalidate anything server-side.** Calling it returns `{"ok": true, "note": "tokens are stateless; discard them client side"}` — a direct admission from the API that despite the docs' claim, no server-side revocation happens.
- **Pagination is offset-based, not page-based.** `?page=1` and `?page=2` (same limit) return byte-identical results; the real, undocumented parameter is `offset`. Live-verified across all three collection endpoints (listings, rentals, projects), not just one.
- **Max page size is 50, not the documented 200.** Anything above 50 is silently clamped.
- **Response shape is `{limit, offset, count, total, has_more, results}`**, not the documented `{total, page, page_size, results}`.
- **`/v1/listings` returns inactive listings too**, contradicting the doc's claim that only active listings come back — evidenced by an undocumented `is_live` field present on every record, roughly 20% of which are `false`.
- **The documented singular `GET /v1/listing/{id}` 404s.** The real path is plural: `GET /v1/listings/{id}`.
- **`GET /v1/listings/{id}/similar` doesn't exist at all.**
- **`GET /v1/analytics/summary` doesn't exist.** Confirmed by also trying about ten plausible alternate paths (`/v1/analytics`, `/v1/stats`, `/v1/insights`, `/v1/dashboard`, etc.) — all 404. This directly shaped the frontend's Insights screen (see Phase G).
- **The documented `/v1/favourites` doesn't exist**, but a real, working endpoint does — found at `/v1/saved` by trying plausible alternates. Its `POST` body field is `listing_id`, not the documented `id` (discovered from the `422` validation error's own message).
- **`project_id` as a filter on `/v1/listings` is silently ignored** — three different `project_id` values all returned the identical, unfiltered full result set. This one mattered enormously later: the documentation's own claim that `project.total_listings` "always agrees with what `GET /v1/listings?project_id=...` returns" is therefore untestable via the documented method, which is exactly why Q10 required an independent client-side join instead.
- Filters that *were* verified to work correctly: `locality`, `bhk`, `min_price`/`max_price`, `furnishing`, `property_type`. Confirming these worked was just as important as finding the ones that didn't — a padded "everything is broken" narrative would have been wrong.

Every one of these — both the confirmed-broken and the confirmed-correct behaviors — was logged in `analysis/INVESTIGATION_LOG.md` with the hypothesis, the test, the result, and the conclusion, because the assignment explicitly said hypotheses that turn out *false* are as valuable to show as the ones that hold up.

## 5. Phase C — Full dataset retrieval

Once the *mechanism* of pagination was understood (offset/limit, not page/total), the complete datasets were downloaded:

- **Listings: 3,500 records.** **Rentals: 1,320.** **Projects: 400.**
- Retrieval used `offset`/`limit=50`, terminating on `has_more: false` — deliberately *not* trusting the API's own `total` field as a stopping condition, because of the next discovery.
- **The API's own `total` field undercounts every collection by ~9.5%.** Listings report `total: 3196` but 3,500 are actually retrievable; rentals report `1205` vs. 1,320 actual; projects report `365` vs. 400 actual. This was verified extremely conservatively: two independent full re-pagings of the listings endpoint, run about a day apart, returned the *exact same* 3,500 unique IDs with zero duplicates — ruling out a live-changing dataset as the explanation, and pointing instead to a stale cached counter that was never updated after more records were added.
- Raw JSON dumps were saved to `analysis/raw/` (gitignored — large, derived, and not something that belongs in version control) via a reproducible download script (`analysis/scripts/download.js`).

## 6. Phase D — Hypothesis-driven analysis

This is where most of the assignment's actual difficulty lived. Each of the ten questions is summarized below with the reasoning that produced the first-pass answer (later stress-tested in Phase E).

### Q1 — total_listing_records
Given the Phase C discovery that `total` is unreliable, "retrievable" (per the assignment's own definition — page to the end with no filters) means the actual count reached by full pagination: **3,500**.

### Q2 — unique_properties (property identity methodology)
The naive idea — group by exact `(latitude, longitude)` — was tried first and rejected: it merged *different* units in the *same building* (same coordinates, different floor/bedroom/price), which would have undercounted properties. A tighter exact match on `(latitude, longitude, floor, bedroom)` was tried next and rejected the other way — it found *zero* duplicates, because independent sources don't geocode a building to bit-identical coordinates.

The methodology that survived scrutiny: group by `(apartment_name, locality, floor, bedroom)`, then within a group require `carpet_area` within 5%, `price` within 15%, coordinates within ~1.1km, and a *different source website* — the last constraint matters because it rules out the same portal listing its own property twice, which isn't what "described by several records" means here. This produced 52 duplicate pairs in the first pass.

### Q3 — active_listings
Direct count of `is_live === true`: **2,792**.

### Q4 — corrupt_listing_ids
Five field-level impossibility checks were run and cross-checked against every `property_type` for legitimate exceptions before anything was classified as corrupt (e.g., `plot` records legitimately have `floor: 0, total_floors: 0`, so that pattern was *not* flagged): negative price, floor exceeding the building's own floor count, carpet area exceeding super built-up area (architecturally impossible), and swapped latitude/longitude (proven, not assumed — swapping the two fields back landed every flagged record exactly inside this city's normal coordinate range). A sixth category — sale prices under ₹30,000 — was initially included too (see Phase E for why it was later removed).

### Q5 — total_monthly_rent
Sum of `price` across rentals filtered to the assigned locality, after normalizing the locality string to the API's lowercase convention (the registration email gave it in Title Case).

### Q6 — avg_price_per_sqft_2bhk
Mean of the *per-record* `price / carpet_area` ratio (not `total price / total area`, per the assignment's explicit instruction) across live, 2-bedroom listings, excluding whatever was identified in Q4 and Q9.

### Q7 — costliest_project
This required resolving a genuinely strange discovery first: `/v1/projects` `price_min`/`price_max` values are small decimals like `1.66` or `41.50` — clearly not raw rupees. Sorting every project's `price_min` across the full dataset revealed a hard, exact numeric gap: every value fell in either `[1.00, 2.09]` or `[41.50, 99.90]`, with *nothing* in between. Converting the low range as Crores (×1e7) and the high range as Lakhs (×1e5) turns that into one smooth, continuous rupee range — exactly the behavior of the Indian real-estate convention of switching display units at the ₹1 Crore threshold. With that conversion applied, the costliest project was **P60060, ₹58,300,000**.

### Q8 — listings_last_7_days
Required figuring out what timezone `listings.posted_at` is actually in, since it carries no `Z` suffix despite the documented "UTC everywhere" convention. This was resolved by cross-referencing against `rentals.posted_at` (which *does* correctly carry `Z`/UTC): both datasets turned out to share one hard generation cutoff at the assignment's `REFERENCE` moment. Rentals cut off exactly at `2026-09-09T18:30:00Z` (the UTC equivalent of `REFERENCE`). Listings' last populated day, by contrast, is filled with entries across the *entire* 24-hour range through `23:46`, with nothing at all the next day — which is only possible if listings' clock is already IST, not UTC (a UTC clock would have been truncated mid-day at 18:30). With that resolved, comparing the naive timestamp strings directly against the IST interval boundaries gave **129**.

### Q9 — fake_listing_ids
The first-pass signal: a `posted_by_contact` phone number associated with more than one distinct `posted_by_name`. Twelve such contacts existed, covering 230 listings.

### Q10 — projects_with_wrong_listing_count
Since the documented `project_id` filter on `/v1/listings` is broken (Phase B), this required an independent client-side join: group all downloaded listings by `project_id`, count them per project, and compare against each project's own `total_listings` field. **295 of 400 projects (73.75%) disagreed** — mostly in the direction of the project under-reporting, consistent with the same stale-counter root cause as the Q1 `total` bug.

Every finding above (and several more granular ones — sort-order violations on `sort_by=posted_at`, an area-unit bug specific to one listing source, and others) was written up as a structured Part 3 finding at this stage, with evidence IDs and a category from the assignment's fixed list.

## 7. Phase E — Independent validation

The instruction for this phase was explicit and important: treat every Phase D answer as a hypothesis to be attacked, not a result to be trusted. A second, independently-written script (`analysis/scripts/validate.js`) deliberately avoided importing any of the Phase D analysis modules, so a bug in the original logic couldn't just get silently re-confirmed by reusing the same code.

This pass **changed three of the ten answers**, materially:

### Q2 revised: 3,448 → 3,254
Testing "normalized-field matching" (as explicitly requested) surfaced a real gap: `apartment_name` values weren't reliably formatted. The *same* building appeared as `"Godrej Residency"`, `"godrej residency"`, `"GODREJ RESIDENCY"`, and `"Godrej  Residency"` (double space) across different sources — and separately, some names used hyphens where others used spaces (`"Casagrand-Residency"` vs. `"Casagrand Residency"`). Exact-string matching in the first pass had silently missed every one of these as duplicates. Re-running the same grouping logic with case/whitespace/hyphen normalization recovered **194 additional genuine duplicate pairs** (verified, not assumed: all 254 total pairs agreed 100% of the time on `furnishing`, `facing_direction`, and `bathroom` — three fields that weren't part of the matching criteria at all, so that level of agreement is powerful independent corroboration). One thing was explicitly checked and *not* merged: names that looked similar by edit distance but were actually different real builder brands (e.g., "Sobha Terraces" vs. "Lodha Terraces" — Sobha and Lodha are both real, distinct Indian developers).

### Q4 revised: 30 → 24 IDs
On reflection, the sub-₹30,000-price category didn't hold up to the assignment's own stated bar. A negative price, a floor number higher than the building has, and a carpet area larger than the super built-up area are all *hard, logical/physical impossibilities* — there is no number that could make them valid. An implausibly low but *positive* price is different in kind: it's a value that could, in principle, exist; it's just extraordinarily unlikely. (Multiplying it by 1000 produces a plausible price, suggesting a scale bug as the likely real-world cause — but the cause being probably-a-typo doesn't make the given value itself impossible.) That category was removed.

### Q9 revised: 230 → 95 IDs
This was the most involved re-investigation. Splitting the 12 multi-name contacts by listing volume revealed something the first pass had missed entirely: the 5 highest-volume contacts (18–35 listings each) price at almost exactly the dataset-wide average rate — no economic behavior consistent with fraud. The other 7 contacts (13–14 listings each) price 44–46% *below* market, and this gap held up even after controlling for bedroom count individually (ruling out a "just sells smaller units" explanation). Digging into *why* these two groups differed: the 5 market-priced contacts cycle only through different individual person names; the 7 underpriced contacts mix in recognizable real-estate agency brand names ("Skyline Homes," "Prime Realty," "Crown Estates," etc.) that — checked across the whole dataset — never appear as any single business's own consistent identity, only ever as one of several rotating aliases on a shared number. The revised, narrower rule (multiple names *and* at least one company-shaped name *and* the pricing anomaly) is what actually matches the assignment's specific definition of fake listings ("exist to generate enquiries"). The excluded 135 listings were left out for lack of evidence, not asserted to be legitimate — a real residual uncertainty, noted honestly rather than papered over.

Q6 was recomputed downstream of the Q4/Q9 revisions (14,465.77 → 14,425.01 — a 0.28% shift, safely inside the assignment's ±1% tolerance, and reassuring evidence that Q6 wasn't fragile to the judgment calls in Q4/Q9). Q1, Q3, Q5, Q7, Q8, and Q10 were independently re-derived and came back unchanged.

## 8. Phase F — Final findings audit

With the ten answers now validated, `statement.md` and `API_REFERENCE.md` were read again in full, and every candidate finding from Phases B–E was checked one more time against the literal documentation text, reduced to a final list of **21 confirmed discrepancies**. Each one was checked against three bars before being kept: personally reproduced (not inferred from wording alone), evidence provided and — this was done programmatically, not just by eye — every evidence ID verified to actually exist in the downloaded dataset and to genuinely demonstrate the claim it was cited for, and using exactly one of the assignment's 13 allowed categories.

A few consolidation calls were made deliberately: four separate `pagination` findings were kept distinct (page ignored, wrong max limit, wrong response shape, wrong `total`) rather than merged, since each is independently actionable; the `/v1/favourites` → `/v1/saved` path issue and its body-field issue were merged into one finding, since they're two symptoms of the same underlying story. The Q4/Q9 investigative work was also written up as its own two Part 3 findings (`data_quality` and `fraud` are both explicitly named allowed categories), separate from being Part 2 answers.

Two small, honest gaps were called out explicitly rather than hidden: six listings carry far-future `posted_at` timestamps (well past the shared generation cutoff established for Q8) that don't fit cleanly into either the corrupt or fake classification given the evidence available, and were left unclassified; and three project records have `price_max` values that don't cleanly resolve under the Lakh/Crore rule either way (though this was shown not to matter — even the most generous possible resolution of those three doesn't change the Q7 answer).

Outputs: `analysis/results/final_answers.json` (machine-readable, generated *programmatically* from the validated results rather than hand-typed, specifically to eliminate transcription risk — an earlier hand-typed draft was caught with a diff check against the script output and discarded) and `analysis/results/final_findings.json`.

## 9. Phase G — Frontend implementation

Only after the above was the frontend started, built against the *verified* API behavior rather than the documentation.

### 9.1 Reading the actual framework docs first

`AGENTS.md` (checked into the repo, auto-generated by `next dev`) warns explicitly that this is Next.js 16, whose conventions may differ from an LLM's training data, and to read the bundled docs in `node_modules/next/dist/docs/` before writing code. This turned out to matter immediately: Next.js 16 renamed `middleware.ts` to `proxy.ts` (same mechanism, new file name and export name), and the docs were consulted specifically to confirm cookie-write constraints (Server Components can read cookies during render but cannot write them — only a Route Handler or Server Function can) before designing the session system.

### 9.2 Architecture

```
lib/ivy/          — typed, server-only client for the Ivy API itself
lib/session*.ts   — encrypted cookie session (read side + shared pure helpers)
proxy.ts          — route protection + transparent token refresh
app/api/...       — the browser's only door to anything Ivy-related
app/...           — pages (Server Components fetching via lib/ivy)
components/       — presentational + the few genuinely interactive bits
```

The browser never talks to `solve.ivy.homes` directly. It talks to this Next.js server, which holds `IVY_API_KEY` and forwards it as the `X-API-Key` header discovered in Phase B.

### 9.3 The session-security decision

The most consequential security decision in the whole build: **the session cookie is encrypted, not just marked `HttpOnly`.**

The reasoning: decoding a real Ivy access token during Phase B investigation showed that its JWT payload embeds the literal shared `IVY_API_KEY` as an internal claim (`"key": "IVY26-..."`). An `HttpOnly` cookie prevents page JavaScript from reading a cookie's value, but it does *not* prevent the browser itself — or a user opening their own browser's DevTools → Application → Cookies panel — from seeing the raw cookie value, which would still be that JWT, trivially base64-decodable to recover the developer's own shared API key. That's a real leak of a credential that matters beyond just "this user's own data" — the assignment's own rules state sharing that key is disqualifying, and this repo's key is used by every visitor to the deployed demo.

The fix: the session payload (access token, refresh token, expiry, email) is AES-GCM encrypted with a key *derived from* `IVY_API_KEY` itself (via a SHA-256 digest of the key plus a fixed context string, run through Web Crypto's `importKey`) before it's ever set as a cookie value. This was deliberately built to need no *new* secret/environment variable, and to use only `crypto.subtle` — which is available identically in both the Node.js runtime (Server Components, Route Handlers) and the Edge-style runtime `proxy.ts` may run under — so the whole scheme stays fully stateless. That statelessness was itself a considered trade-off: an in-memory server-side session store was considered and rejected, because it would silently break the moment this app is deployed to a serverless platform like Vercel, where different requests can land on different, non-memory-sharing instances.

This was caught and fixed *during* the build, not designed perfectly up front — the first cut of the session cookie stored the JWTs directly, and a `curl`-based test that deliberately inspected the raw cookie jar contents (not just checked that login "worked") is what surfaced it.

### 9.4 Token refresh

Access tokens last 15 minutes, and Server Components can't write cookies — so `proxy.ts` is the single place that checks whether the current token is within 60 seconds of expiring and, if so, calls the (undocumented, Phase B-discovered) `/auth/refresh` endpoint and rewrites the cookie on the outgoing response before the request ever reaches a page. Every Server Component downstream can then just *read* an already-fresh session. A small client-side `SessionKeepAlive` component pings a no-op route every 5 minutes so a tab left open with zero navigation for 30+ minutes still gets refreshed in the background, directly satisfying the assignment's "still working 30 minutes after login" requirement even in the passive-tab case.

### 9.5 Building each required capability

- **Login** — a client form posts to `/api/auth/login`, which calls the real login flow and sets the encrypted cookie. All three demo accounts (`demo1`/`demo2`/`demo3@ivy.homes`) were tested directly against the running app, not assumed to work from the API-level test alone.
- **Listings** — offset/limit pagination (never the documented `page` param), with locality/bedroom/price-range/furnishing/property-type filters. Every filter is applied server-side *and* re-checked against the same filter client-side after the response comes back — belt-and-suspenders, so a UI filter can never silently show a mismatched result even if the API's own filtering behavior were to change later.
- **Listing detail** (`/listings/[id]`) — fetches by ID server-side, so a direct URL paste works exactly like clicking through from the list. Uses the real plural path from Phase B, not the documented (404ing) singular one.
- **Saved listings** — backed by the real `/v1/saved` endpoint (not the documented, nonexistent `/v1/favourites`) with the real `listing_id` body field (not the documented `id`). Deliberately *not* implemented with `localStorage`, since the assignment explicitly disallows faking persistence that way — this is the user's actual account state on the Ivy API, so it survives reload and logout/re-login by construction, not by any extra effort.
- **Rentals & Projects** — same verified-filter pattern as listings for rentals; for projects, `price_min`/`price_max` are run through the Q7 Lakh/Crore conversion before ever being displayed, rather than showing the misleading raw values.
- **Insights** — built with the explicit premise that `/v1/analytics/summary` does not exist. Instead of faking that endpoint, the page pages through the *entire* live dataset (offset/limit, fetched in small concurrent batches to keep load time reasonable) and computes every statistic itself, applying the same corrections used throughout the investigation. The page also surfaces the investigation's own findings directly to a human — the API's undercounted totals, how many projects have a wrong listing count, and the data-quality/fraud counts — which is explicitly what the assignment asks this screen to do. Results are cached in-memory for 30 minutes, since a full recompute is an expensive full-dataset scan and this data isn't user-specific.

### 9.6 Bugs caught by actually using the app (not just by the code compiling)

Manual QA — first via `curl` for auth/session/API-shape checks, then via a headless browser (login, click through, save/unsave, resize to a 390px mobile viewport, read the actual rendered numbers) — caught two real, non-cosmetic bugs that a type-check or a lint pass would never have found:

1. **A listing card showing "3 BHK, 106 sqft."** The magichomes square-meter-to-square-feet correction (discovered in Phase D) had been applied inside the Insights aggregation code, but never wired into the actual listings browse/detail/saved data path — so real listings were rendering with the wrong, tiny raw area. Fixed by centralizing the correction into one shared `correctListingAreas` helper and applying it at every point a `Listing` is fetched.
2. **The Insights page showing "29 data-quality issues" instead of the validated 24.** Tracing it down: the shared correction helper's first draft checked the sqm threshold *independently* on `carpet_area` and `super_built_up_area`, but the proven Phase D/E methodology decides the conversion *once*, from `carpet_area` alone, and applies it to both fields together. Because `super_built_up_area` runs about 1.3–1.4× `carpet_area`, a record near the boundary could have its carpet area converted while its super built-up area was left unconverted (since it independently sat just above the threshold) — fabricating a false "carpet exceeds super built-up" violation that didn't exist in the real data. Fixed by making the conversion decision once and applying it atomically to both fields, matching the analysis script exactly, and reverified against a fresh live re-fetch of the dataset (not just the cached snapshot) to make sure this wasn't a live-data-drift coincidence.

A third, smaller issue was also fixed proactively: the Insights "recently posted" count was initially anchored on the raw *maximum* `posted_at` in the dataset, which — because of the six far-future anomalous timestamps mentioned in Phase F — put the "last 7 days" window in a sparse, mostly-empty period and made the metric look broken (it showed "1"). Anchoring instead on the 99th percentile of `posted_at` (excluding the top ~0.17% as statistical outliers, without hardcoding any assignment-specific date) fixed it to a sensible number while staying a general, non-arbitrary rule.

### 9.7 Testing methodology

- `npx tsc --noEmit` and `npm run lint` were run after every meaningful change, not just once at the end.
- `npm run build` (production build) plus `npm run start`, tested against the actual running server — not just `next dev`.
- Real login with real demo credentials via `curl`, inspecting the actual `Set-Cookie` response (this is what caught the plaintext-JWT-in-cookie issue).
- A scripted headless-browser pass exercising the full user journey: login → browse → filter → click into a listing → save it → confirm it persists on `/saved` → browse rentals/projects → load Insights → resize to mobile width and check for horizontal overflow. Zero console errors were observed throughout; the only "failed requests" reported were harmless aborted Next.js route-prefetch requests from rapid scripted navigation, not real errors.
- Screenshots were captured and read at both desktop and 390px-wide mobile viewports to visually confirm layout, not just to check that HTTP status codes were 200.

### 9.8 A known, accepted limitation

Direct navigation to a nonexistent listing ID correctly renders the "Listing not found" UI, but returns an HTTP `200` rather than a `404`. This was investigated against the Next.js docs rather than assumed to be a bug in the app: because the route has a `loading.tsx` (a streaming Suspense boundary), the response has already started streaming as `200` by the time `notFound()` is called deep in the render, and per Next.js's own documentation, the status genuinely cannot change once streaming has begun. Fixing it would require checking listing existence inside `proxy.ts` before the page even starts rendering — extra latency on every single listing view, for a cosmetic status-code correctness issue that doesn't affect any real user or grader interaction with an authenticated internal tool. Documented here rather than silently left for someone else to "discover" as an apparent bug.

### 9.9 Commit structure
